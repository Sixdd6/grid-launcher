# 10 — Game identity, update detection, and app version

## Purpose

This document describes how GRID Launcher decides that "this server game" and "this
locally installed game" are the same thing, how it decides that a newer copy exists on
the server, and how the application knows its own version string.

Three separate identity/version concerns are covered, and they must not be conflated:

1. **Game identity** — matching a server catalog entry to an installed library record
   (`grid_launcher/library/identity.py`). Everything in the install registry, cloud sync,
   cover cache, and details view depends on this.
2. **Game update detection** — deciding whether the server holds a newer build of an
   already-installed game (`grid_launcher/library/update_detection.py`), plus the
   per-platform meaning of "update".
3. **Application self-version** — the launcher's own version string
   (`grid_launcher/version.py`, generated by `build.sh`).

Explicitly out of scope, with cross-references:

- **Emulator source version checks** (GitHub/Gitea release tag vs. installed emulator
  version) are a different mechanism entirely — see `docs/porting/04-emulator-launch.md`
  and `tests/test_source_version_check.py`.
- **The installed-record field list and the download/extract pipeline** — see
  `docs/porting/03-library-install.md`. This document only covers the identity-bearing
  fields of that record.
- **Provider metadata merge inside one ROM item** (LaunchBox/IGDB/ScreenScraper blocks) —
  see the "Metadata merge" section of `docs/porting/01-romm-api.md`. That merge never
  crosses game boundaries; see Behavior below.
- **Cover cache file naming**, which uses its own identity basis — see
  `docs/porting/07-covers-images.md`.

---

## External surfaces

Identity and update detection introduce no network, file, or process surfaces of their
own. They read data already fetched by the catalog layer and already persisted by the
config layer.

Two surfaces belong to the app-version concern:

- **`grid_launcher/version.py`** — a generated Python source file containing a single
  `__version__` string. It is written by `build.sh` at build time
  (build.sh:99–103) and is gitignored, so it is absent in a source checkout.
- **AppImage update metadata** — an `update_info` string embedded in the AppImage by
  `appimagetool`, of the form
  `gh-releases-zsync|Sixdd6|grid-launcher|latest|grid-launcher-*-x86_64.AppImage.zsync`
  (build.sh:228, .github/workflows/appimage-linux.yml:89). A companion `.zsync` file is
  produced only when `zsyncmake` is available (build.sh:229–238). This is consumed by
  external tooling (AppImageUpdate); **the application itself never reads it and never
  contacts GitHub about its own version** — see Behavior, "App version flow".

## Data model (identity key formats)

### Key 1 — `game_key` (title/platform pair)

`game_key(game)` returns an ordered pair built from two fields (identity.py:4–5):

| Component | Source field | Normalization |
| --- | --- | --- |
| title | `title` | trim surrounding whitespace, then **lowercase** (`str.lower`) |
| platform | `platform` | trim surrounding whitespace, then **lowercase** (`str.lower`) |

Missing fields default to the empty string, so `game_key({})` is `("", "")` — a valid,
non-null key. There is no type guard: a non-string `title` or `platform` raises.

Note the normalization asymmetry: `game_key` uses `lower`, while `rom_id_key`
(below) and nearly every platform predicate use `casefold`. For ASCII these agree; they
diverge for characters such as `ß`/`ss` and `İ`. Test doubles throughout the suite
implement `_game_key` with `casefold` (for example tests/test_update_detection.py:335–339,
tests/test_install_metadata.py:17–21), so the tests do not pin the `lower` behavior.

### Key 2 — `rom_id_key` (server ROM id)

`rom_id_key(game)` returns a single string (identity.py:8–12):

- read field `rom_id`;
- if it is not a string, return `""` (this is a real type guard, unlike `game_key`);
- otherwise trim and casefold.

The value originates from the RomM ROM item's `id`, stringified
(grid_launcher/server/catalog.py:290, `:354`). It is numeric in practice, so casefolding is
a no-op, but the comparison is defined as a case-insensitive string comparison, not a
numeric one.

### Key 3 — cloud sync state key (derived, string form)

`cloud_sync_state_key` (grid_launcher/library/cloud_sync.py:64–75) collapses the two keys
above into one namespaced string for map lookups:

- `rom:<rom_id_key>` when the ROM id is non-empty;
- otherwise `name:<title>::<platform>` from `game_key`;
- `""` when both title and platform are empty (an unusable key; callers treat it as
  "no state", cloud_sync.py:86–88).

Full semantics in `docs/porting/06-cloud-saves.md`.

### Key 4 — details ROM-id cache key (derived, string form)

`details_rom_id_cache_key` (grid_launcher/server/details_cache.py:97–107) is
`"<title>::<platform>"` from `game_key`, and returns `""` if **either** component is
empty. Unlike key 3 it never uses the ROM id — it is the cache key *for* a resolved ROM id.

### Key 5 — cover cache key (derived, filename-safe)

`installed_cover_cache_key` (grid_launcher/cover/utils.py:205–217) is a *different*
identity: basis = trimmed `rom_id` if present, else `"<title>|<platform>"` with original
case preserved; the basis is SHA-1 hashed and truncated to 12 hex chars and prefixed with
a sanitized 48-char title. Case is **not** folded here. Covered by
`docs/porting/07-covers-images.md`; listed here so a port does not accidentally reuse
`game_key` for cover filenames.

### Key 6 — TV backend identity (divergent)

The TV/QML backend does not use `identity.py` at all. Its install registry replaces
entries by exact, case-sensitive string comparison of `id` **or** `rom_id`
(grid_launcher/tv/bridge/game_backend.py:691–698), and its native-executable lookup
matches `str(g["rom_id"]) == rom_id` exactly (game_backend.py:736). There is no
title/platform fallback on the TV side.

### Identity-bearing fields of the installed record

The persisted installed-game record (full field list in `docs/porting/03-library-install.md`)
carries these identity/version fields:

| Field | Written by | Meaning |
| --- | --- | --- |
| `title`, `platform` | install_registry.py:27–28 | components of `game_key` |
| `rom_id` | install_registry.py:37 | components of `rom_id_key` |
| `ra_id` | install_registry.py:38 | RetroAchievements game id (identity for achievements, not for matching) |
| `server_updated_at` | install_registry.py:39 | server-side modification timestamp captured at install time |
| `rom_file_name` | install_registry.py:40 | server filename; carries the embedded version tag for Windows titles |
| `revision` | install_registry.py:56 | version string from metadata or from `game.json` |
| `update_available` | install_mixin.py:153, `:197` | **transient** in-memory flag, `"true"`/`"false"` |

`update_available` is not in the normalizer's whitelist (grid_launcher/core/config.py:152–184),
so it is stripped every time the library list is normalized and therefore never persisted.
The same is true of `revision`, `languages`, `tags`, `fanart_url`, `companies`,
`first_release_date`, `rom_base_file_id`, and the PS4/Xbox 360 file-id maps — they are
written by `build_installed_game_record` but dropped by `normalize_installed_games`.

### Version tag formats inside `rom_file_name`

Two mutually exclusive tag shapes are recognized (update_detection.py:8–9):

| Kind | Pattern (case-insensitive) | Example | Parsed value |
| --- | --- | --- | --- |
| numeric | `(v` + exactly 5 digits + `)` | `My Game (v00042).zip` | integer `42` |
| semver | `(v` + one or more dot-separated digit groups + `)` | `A Little to the Left (v3.6.0) (2022) (W_P).7z` | string `"3.6.0"` |

`rom_file_name_version` (update_detection.py:20–31) tries numeric first, then semver, and
returns `null` when neither matches. `(v1234)` (four digits) matches neither pattern —
the numeric pattern needs exactly five digits and the semver pattern needs a dot
(tests/test_update_detection.py:174–176).

The value returned is a *tagged union*: integer for numeric, string for semver. A port
must preserve that distinction, because comparison refuses to mix kinds (see Behavior).

### Update-detection timestamp field precedence

`game_server_updated_at` (update_detection.py:12–17) reads the first of these that is a
non-blank string, and returns the trimmed value: `server_updated_at`, then
`rom_updated_at`, then `updated_at`. Returns `""` if none qualifies. Only
`server_updated_at` is actually produced by the catalog layer (catalog.py:355); the other
two are compatibility fallbacks (tests/test_update_detection.py:156–160).

## Behavior

### Matching algorithm — full fallback order

`games_match_identity(left, right)` (identity.py:15–20) is the single matching primitive.
It is symmetric and has exactly two branches:

1. Compute `rom_id_key` for both sides.
2. **If both are non-empty**, the result is `left_rom_id == right_rom_id`. Title and
   platform are not consulted at all — two records with the same ROM id match even if
   their titles differ, and two records with *different* ROM ids do **not** match even if
   title and platform are identical.
3. **Otherwise** (either side missing a ROM id), the result is
   `game_key(left) == game_key(right)`.

There is no third fallback (filename, file size, hash, path). Nothing in the codebase
compares file hashes or file ids for identity.

Two derived helpers scan a list with this predicate:

- `is_game_installed(game, library_games)` — true if **any** library entry matches
  (identity.py:23–24).
- `installed_game_record(game, library_games)` — returns the **first** matching entry in
  list order, or null (identity.py:27–31).

The main window exposes all four as thin delegates (grid-launcher.py:3223–3236), reading
`self.library_games` as the library list.

#### Server-side lookup uses a different, per-entry order

`_server_game_for_identity(game, rom_id)` (grid-launcher.py:3395–3405) does **not** call
`games_match_identity`. It walks the server catalog, keyed by platform label, and for each
server entry in turn tests:

1. `rom_id` (the *argument*, trimmed and casefolded) is non-empty **and** equals the
   server entry's `rom_id_key` → return that entry;
2. otherwise `game_key(server_entry) == game_key(game)` → return that entry.

Because both tests are applied per entry before moving to the next entry, a title/platform
match on an **earlier** entry wins over a ROM-id match on a **later** entry. This is the
opposite of a two-pass "ROM id first, then name" search. The iteration order is the
insertion order of the platform map, which is populated as asynchronous per-platform
fetches complete (grid-launcher.py:3138), so the order is not deterministic across runs.

`hydrate_install_game_metadata` (grid_launcher/library/install_metadata.py:52–96) uses the
same per-entry disjunction — `rom_id_key(server_game) == rom_id.casefold() or
game_key(server_game) == target_key` (install_metadata.py:56) — and stops at the first
match, copying only fields that are currently empty on the target. Record-format details
are in `docs/porting/03-library-install.md`; the point relevant here is that hydration
matching is *not* `games_match_identity` and can therefore attach a differently-identified
server entry's metadata to a game.

`sync_install_metadata_to_details_game` (install_metadata.py:114–143) guards on
`game_key` equality only (install_metadata.py:120) — the currently open details game must
have the same title/platform pair as the install record, or nothing is copied.

`resolve_rom_id_for_game` (grid_launcher/server/details_cache.py:197–223) resolves a
missing ROM id in three steps: the game's own non-empty `rom_id`; then the details ROM-id
cache under key 4; then the first server entry whose `game_key` matches, taking its
non-empty `rom_id`. Returns `""` when all three fail.

#### Collision behavior

`game_key` is the de-duplication key for the persisted library.
`normalize_installed_games` (grid_launcher/core/config.py:106–190) walks the stored list,
drops entries whose `title` or `platform` is missing or blank (config.py:118–123), and
keeps only the **first** entry per `game_key`; later duplicates are silently discarded
(config.py:185–188). This normalization runs on config load (grid-launcher.py:478), before
every persist (grid-launcher.py:3239), and immediately after registering a new install
(install_mixin.py:135).

Registration is likewise `game_key`-scoped: `_register_installed_game` removes every
existing entry with the same `game_key` before appending the new record
(install_mixin.py:126–134). Consequence: **two distinct server games that share a
title/platform pair cannot both be installed**, even if their ROM ids differ. The second
install evicts the first from the registry (the first install's files are not removed by
this path).

Uninstall and cleanup are also `game_key`-scoped (grid_launcher/library/install_registry.py:93–108,
grid_launcher/library/install_cleanup.py:109–114), as is the install queue
(grid_launcher/library/install_state.py:7–25).

The `installed_game_update_keys` set that caches "has an update" is a set of `game_key`
pairs (grid-launcher.py:480), inheriting the same collision domain.

### Update detection flow

#### The decision function

`game_has_server_update(installed_game, server_game, is_emulators_platform=…)`
(update_detection.py:97–122) returns a boolean, evaluated in this order:

1. **Emulator veto.** If either side is on the `Emulators` platform, return false
   (update_detection.py:103–105). The platform predicate is injectable; the default
   compares `platform` trimmed and casefolded against `"emulators"` (update_detection.py:103).
   Emulator updates are handled by the source-version mechanism in doc 04.
2. **Windows/PC filename-version check.** If either side's platform contains `"windows"`
   or equals `"pc"` (update_detection.py:73–80), compare the embedded version tags of
   `installed_game["rom_file_name"]` and `server_game["rom_file_name"]` via
   `has_newer_server_rom_version`. If that says the server is newer, return true
   immediately (update_detection.py:107–111). If it says no, **fall through** to the
   timestamp check — a false here is not a veto.
3. **Timestamp check.** Parse the installed record's timestamp
   (`game_server_updated_at` → `_parse_timestamp`). If it is absent or unparseable, return
   false (update_detection.py:113–116). This is the deliberate "legacy install" case:
   records written before `server_updated_at` existed never report an update
   (tests/test_update_detection.py:129–140). Then parse the server timestamp; if absent or
   unparseable, return false. Otherwise return `server > installed` — strictly greater,
   so equal timestamps mean no update (update_detection.py:118–122).

`_parse_timestamp` (update_detection.py:83–94) accepts ISO-8601, replacing every `Z` in the
string with `+00:00` (an unconditional global replace, not anchored to the end;
update_detection.py:87), and assumes **UTC** for naive timestamps. Unparseable input yields null,
never an exception.

#### Version-tag comparison

`has_newer_server_rom_version(installed_name, server_name)` (update_detection.py:56–70):

1. Parse both names into `(kind, parts)` where kind is `"numeric"` or `"semver"`
   (update_detection.py:34–41); semver parts are the dot-separated integers.
2. If **either** side has no recognizable tag, return false (update_detection.py:59–60).
   An untagged server file therefore never triggers an update.
3. If the kinds differ, return false — a numeric tag is never compared against a semver
   tag (update_detection.py:64–65, tests/test_update_detection.py:226–238).
4. Numeric: `server > installed` on the single integer.
5. Semver: left-to-right component comparison, zero-padding the shorter side to the longer
   length; the first differing component decides; equal throughout means false
   (update_detection.py:44–53). So `1.2` vs `1.2.0` is not an update, and `1.2` vs `1.2.1` is.

Note the semver parse in `_rom_file_name_version_for_compare` calls integer conversion on
each dotted component without a guard (update_detection.py:39); the regex only admits
digits, so this cannot fail for values that regex produced.

#### When checks run

`_refresh_installed_game_update_state` (install_mixin.py:141–173) recomputes the whole
library's update state. It has six call sites (grid-launcher.py:2818, :3134, :3139;
install_mixin.py:136, :1156; details_view_mixin.py:1823), covering these triggers:

| Trigger | Anchor |
| --- | --- |
| A platform's server games finished loading (success **or** failure) | grid-launcher.py:3134, `:3139` |
| A game finished installing / was registered | install_mixin.py:136 |
| A game was uninstalled | install_mixin.py:1156 |
| Server connection data was cleared (disconnect) | grid-launcher.py:2818 |
| The update action found the server entry gone | details_view_mixin.py:1823 |

There is no timer, no polling, and no check at application startup independent of the
server catalog load. If the launcher never connects, no game ever reports an update.

The refresh loop, per installed game:

1. Skip the server lookup entirely for emulator-platform entries (install_mixin.py:145).
2. Otherwise resolve the server entry with `_server_game_for_identity(installed_game,
   installed_game["rom_id"])` and call `game_has_server_update` (install_mixin.py:146–152).
3. Write `update_available` = `"true"`/`"false"` onto the installed record, and collect
   the `game_key` into a fresh set assigned to `installed_game_update_keys`
   (install_mixin.py:153–157).
4. If a details page is open, recompute its flag and refresh **only** the update button —
   text, visibility, enabled state — rather than the full action-button set
   (install_mixin.py:158–173, and the test asserting the full refresh is not called,
   tests/test_update_detection.py:370–372).

`_details_update_available_for_game(game)` (install_mixin.py:176–202) is the per-game
query used by the details page. Order: emulator platform → false; no installed record →
false; `game_key` already in `installed_game_update_keys` → true (cache hit, no server
lookup); otherwise resolve the server entry and evaluate `game_has_server_update`, writing
both the record's `update_available` field and the cache set (adding on true, discarding on
false). The cache is positive-only in the fast path — a stale "true" is returned without
re-verification.

#### How an available update is surfaced

- **Library/Discover cards**: a "Update Available" label whose visibility is driven by the
  truthiness of the card game's `update_available` string (game_views.py:356–360). The
  truthiness test accepts `1/true/yes/on/y/t`, case-insensitively (game_views.py:271–279).
  Because the flag lives on the record, cards reflect it only after the grid is rebuilt.
- **Details page**: `_has_update_available` prefers the window's
  `_details_update_available_for_game` when present, and only falls back to reading the
  `update_available` / `has_update` / `ps4_has_update` fields when it is absent
  (game_views.py:282–294). It short-circuits to false when the game is not installed
  (game_views.py:283–284).
- **Update button**: visible only when the game is installed, is not an emulator entry,
  and an update is available (game_views.py:735, `:741–752`). It is disabled while an
  install is in flight.
- **Button label**: `_details_update_button_text_for_game` (grid-launcher.py:3300–3325)
  returns `"Update to v<tag>"` when — and only when — the installed and server
  `rom_file_name` tags compare as newer *and* the server tag formats non-empty; every
  other path returns plain `"Update"`. Formatting: numeric tags render zero-padded to five
  digits (`v01234`), semver tags render verbatim with a `v` prefix (grid-launcher.py:3273–3280).

#### Performing the update

`_perform_game_update_action` (details_view_mixin.py:1803–1884):

1. Guard: details game exists, is installed, and `_details_update_available_for_game` is
   true (details_view_mixin.py:1804–1809).
2. Resolve the ROM id and cache it on the details game (details_view_mixin.py:1811–1814).
3. Look up the server entry. If it is gone, warn "A newer server version is no longer
   available for this game.", re-run the full refresh, and abort
   (details_view_mixin.py:1816–1824).
4. Copy the server entry into `update_game` and re-resolve its ROM id; abort with a
   warning if empty (details_view_mixin.py:1826–1830).
5. Branch on `is_native_executable_platform` (platform starts with `"windows"`,
   grid_launcher/emulator/selection.py:145–150):
   - **Native**: require an installed record and an existing `extracted_dir` on disk,
     else warn and abort. Then show a modal confirmation stating that saves and
     configuration will be preserved; a non-Yes answer aborts. Set
     `_install_mode = "native_update"` and carry `extracted_dir`,
     `native_executable_path`, and `native_launch_parameters` forward from the installed
     record (details_view_mixin.py:1839–1865).
   - **Everything else**: set `_install_mode = "update"` (details_view_mixin.py:1867).
6. Hydrate metadata, resolve the server ROM filename (abort with a warning if the server
   returns nothing usable), set `rom_file_name`, sync the metadata onto the open details
   game, and hand off to the normal asynchronous install
   (details_view_mixin.py:1868–1884).

The `_install_mode` value then steers three later decision points:

- `_start_async_install` treats `"update"` like a base install for blocking checks
  (install_mixin.py:1163–1184).
- The download-complete handler skips its "already installed, nothing to do"
  short-circuit for modes `ps4_content`, `xbox360_content`, `update`, `source_emulator`,
  and `source_emulator_update` (install_mixin.py:1554).
- The finalize worker dispatches `native_update` to `_apply_native_game_update_without_ui`
  instead of the normal prepare step (install_mixin.py:1591–1592,
  grid_launcher/background/workers.py:561–566).

`prepare_native_game_update_without_ui`
(grid_launcher/library/archive_preparation.py:1264–1348):

1. Copy the installed record, then overwrite from the update payload any non-empty value
   among `rom_id`, `rom_file_name`, `server_updated_at`, `description`, `rating`, `genres`,
   `regions`, `filesize_bytes`, `screenshot_urls`, `ra_id`
   (archive_preparation.py:1294–1308). Refreshing `server_updated_at` here is what makes
   the update flag clear afterwards.
2. Require a non-blank `extracted_dir` that exists and is a directory; otherwise return a
   null record plus an error string (archive_preparation.py:1310–1316).
3. Merge the archive into the install directory (archive_preparation.py:1321–1328). Merge
   semantics (`merge_archive_into_directory`, archive_preparation.py:1236–1261): extract
   into a temp directory chosen on the same filesystem, then merge the tree over the
   target. Files present in the target but absent from the archive are left untouched —
   this is what preserves saves and configuration. The temp directory is removed in a
   `finally` block on both success and failure.
4. Re-detect the launch executable, but only overwrite `extracted_path` when the record
   has no manual `native_executable_path` override (archive_preparation.py:1331–1336).
5. Delete the downloaded archive; a deletion failure becomes a non-fatal warning string
   rather than an error (archive_preparation.py:1339–1346).

The caller resolves the installed record by identity first, falling back to the update
payload itself if none is found (install_mixin.py:794). The temp directory defaults to a
sibling of `extracted_dir` named `<sanitized-title>-temp`, falling back to the system temp
directory (install_mixin.py:806–820).

On success the prepared record is registered through the normal path, which removes the
old `game_key` entry and re-adds the merged one, then re-runs the update refresh
(install_mixin.py:1679–1688). A success toast reads `Updated '<title>' successfully.`

For non-native `"update"` mode there is no merge step: the flow falls through to
`_register_installed_game`, which evicts the old entry by `game_key` and appends the newly
prepared one (install_mixin.py:1691) — a plain replacement of the ROM.

### Native game version detection

Two independent sources produce a version for a native/Windows game. Neither is related to
the application's own version.

**Source A — the filename tag.** `rom_file_name_version` on `rom_file_name`, as described
above. `_details_version_label_text_for_game` (grid-launcher.py:3283–3297) reads it from
the passed game, and if that yields nothing, retries against the installed record's
`rom_file_name`; the formatted result renders as `Version: v01234` / `Version: v3.6.0`.
When no tag is found it falls back to the `revision` field, and finally to an empty string
(which hides the version row, game_views.py:554–571).

**Source B — `game.json`.** For native platforms the installer fetches a server-side
`game.json` file entry before finalizing (install_mixin.py:1563–1566, `:911–940`). It is
downloaded via the ROM content endpoint with an explicit `file_ids` selector, written into
the game's home directory, and parsed by `parse_windows_game_json`
(grid_launcher/library/install_metadata.py:146–186), which extracts:

| JSON key | Record field | Conversion |
| --- | --- | --- |
| `version` | `revision` | stringified; `null` becomes `""` |
| `year`, else `release_year` | `first_release_date` | coerced through integer; non-numeric becomes `""` |
| `tags` (list of strings) | `tags` | comma-joined; ignored unless every element is a string |
| `included_dlc` (list) | `included_dlc` | re-serialized as JSON; defaults to `"[]"` |
| `name` | `name` | stringified, but deliberately **not** applied to the game record |

`apply_windows_game_json_to_game` (install_metadata.py:189–201) writes `revision`,
`first_release_date`, and `tags` only into fields that are currently empty, and always
overwrites `included_dlc`. Malformed JSON, non-dict JSON, or a decode error all yield an
empty parse result, which is a no-op.

`game.json` is excluded from archive selection: `select_native_archive_entry`
(install_metadata.py:217–243) skips any entry named `game.json` (case-insensitive) and any
entry containing a path separator, prefers the first remaining entry with a known archive
extension, and otherwise takes the first remaining top-level entry.

`revision` participates in update detection only indirectly — it is displayed, never
compared. The only version comparison for native games is Source A's filename tag.

### App version flow

1. `build.sh` derives the version from git: `git describe --tags --always --dirty`, with
   the literal fallback `0.0.0-dev` when git fails, then strips a leading `v`
   (build.sh:94–95).
2. It writes `grid_launcher/version.py` containing `__version__ = "<VERSION>"`
   (build.sh:98–103). The file is generated per build and is not checked in.
3. At import time the package tries `from grid_launcher.version import __version__` and,
   on `ImportError`, falls back to the string `"0.0.0-dev"`
   (grid_launcher/__init__.py:12–15). A source checkout therefore reports `0.0.0-dev`,
   identical to a git-less build.
4. The only consumer is the main window title: `GRID Launcher <version>`
   (grid-launcher.py:55, `:295`).

**The application never compares its own version to anything.** There is no in-app update
check, no request to `api.github.com` about this repository, and no `releases/latest`
call for the launcher itself. The `releases/latest` requests in
`grid_launcher/background/workers.py:214`, `:475`, `:479` belong to the **emulator source**
version check (doc 04), and the single "Could not check for updates" message
(grid_launcher/ui/mixins/emulator_ui_mixin.py:1332) is that same emulator flow. Launcher
self-update is delegated entirely to external AppImage tooling via the embedded
`update_info`/zsync metadata described under External surfaces.

## Invariants and error handling

1. **Matching is symmetric and total.** `games_match_identity` never throws for
   string-typed inputs and always returns a boolean; `rom_id_key` tolerates non-string
   `rom_id`, but `game_key` does not tolerate a non-string `title`/`platform`
   (identity.py:5 has no isinstance guard, unlike identity.py:10).
2. **ROM id dominates when both sides have one.** Title/platform is only ever a fallback
   for records lacking a ROM id — chiefly legacy installs and locally added games.
3. **`game_key` is the uniqueness domain of the library.** At most one installed record
   may exist per `(lowercased title, lowercased platform)`; duplicates are dropped by the
   normalizer keeping the first (config.py:185–188) and evicted by registration
   (install_mixin.py:126).
4. **A blank title or platform disqualifies a record from persistence.**
   `normalize_installed_games` skips such entries entirely (config.py:118–123).
5. **`update_available` is derived state, never persisted.** It is absent from the
   normalizer whitelist, so any value read back from config is always missing. It must be
   recomputed after every library load.
6. **Ordering constraint on refresh.** `_register_installed_game` normalizes the library
   *before* recomputing update state (install_mixin.py:135–136); reversing that order
   would discard the flags it just wrote.
7. **Legacy installs never report updates.** A missing or unparseable
   `server_updated_at` on the installed side is an early false, by design
   (update_detection.py:113–116).
8. **Equal timestamps are not an update.** Strict `>` (update_detection.py:122).
9. **Unrecognized or mismatched version tags never produce an update.** Missing tag on
   either side, or numeric-vs-semver, both return false rather than guessing
   (update_detection.py:59–65).
10. **Emulator entries are excluded at two levels** — inside `game_has_server_update`
    (update_detection.py:103–105) and again by the caller before it even looks up a server
    entry (install_mixin.py:145).
11. **Timestamp parsing failures are values, not exceptions.** `_parse_timestamp` catches
    the parse error and returns null (update_detection.py:89–92).
12. **The native update path fails closed.** A missing or non-existent `extracted_dir`
    returns `(null, error message)` and the finalize worker converts that into a failed
    download entry plus a modal warning; the downloaded archive is deliberately kept so a
    retry need not re-download (install_mixin.py:1643–1653).
13. **Merge temp directories are always cleaned.** Both on success and on failure
    (archive_preparation.py:1255–1261; asserted by
    tests/test_native_game_update.py:83–114).
14. **A manual executable override survives an update.** `native_executable_path`, when
    set, suppresses the re-detected `extracted_path` write
    (archive_preparation.py:1334–1336).
15. **The update button label degrades to `"Update"` on every failure path** rather than
    showing a partial or wrong target version (grid-launcher.py:3300–3325).
16. **The app-version import fallback is exactly `"0.0.0-dev"`** and is exercised by test
    (tests/test_version_detection.py:31–46).

## Platform differences

| Platform group | Predicate | What "update" means |
| --- | --- | --- |
| `Emulators` | `platform == "emulators"` (casefolded) — grid_launcher/emulator/selection.py:138–142 | Nothing here. Excluded from `game_has_server_update` and from the refresh loop. Emulator updates use the source release-tag check (doc 04, `_install_mode = "source_emulator_update"`). |
| Windows / PC | `"windows" in platform or platform == "pc"` (casefolded) — update_detection.py:73–80 | Filename version tag first, then the timestamp rule. Update is applied as an in-place **merge** into `extracted_dir`, preserving files not present in the new archive. |
| Native executable (install pipeline) | `platform.startswith("windows")` — grid_launcher/emulator/selection.py:145–150 | Selects the `native_update` install mode and the merge path. **Note the mismatch**: a game on a platform literally named `PC` satisfies the version-tag branch of update *detection* but not the native-executable branch of update *application*, so it would be updated by plain reinstall. |
| PS4 | `platform in {"ps4", "playstation 4", "playstation4", "sony playstation 4"}` — grid-launcher.py:3252–3255 | Two unrelated concepts share the word "update". (a) The generic server-side newer-build check above. (b) **Patch content**: the server exposes per-file `category` values; entries categorized `update` or `dlc` are collected into `ps4_file_ids_by_category` and flagged as `ps4_has_update` / `ps4_has_dlc` (grid_launcher/server/catalog.py:296–301, `:360–362`). These are installed through a separate action with `_install_mode = "ps4_content"` and a kind of `update` or `dlc` (details_view_mixin.py:1525–1568), producing button text `Install Update` / `Install DLC` / `Install Update/DLC` (install_mixin.py:271–279, with the available-kind probe at install_mixin.py:263–268). Installing PS4 patch content does **not** go through `game_has_server_update` and does not clear `update_available`. |
| Xbox 360 | `is_xbox360_platform` (grid-launcher.py:3258–3260) | Same dual meaning as PS4, with `xbox360_has_update` / `xbox360_has_dlc` / `xbox360_file_ids_by_category` (catalog.py:299–301, `:363–365`) and `_install_mode = "xbox360_content"` (details_view_mixin.py:1646, `:1695`). |
| Everything else (console ROMs) | — | Timestamp comparison only; the update is a plain re-download and replacement of the installed record (`_install_mode = "update"`, install_mixin.py:1691). |

Cross-cutting: the details-page field-copy list includes both `ps4_has_update` and
`xbox360_has_update` (details_view_mixin.py:130–136), so those flags travel with the
details game and can be read by the field-based fallback in `_has_update_available`
(game_views.py:290) if the window lacks the richer predicate.

The **TV frontend has no update detection at all** — no reference to
`game_has_server_update`, `update_available`, or `identity.py` exists under
`grid_launcher/tv/`.

## Concurrency

Everything in `identity.py` and `update_detection.py` is a pure function of its arguments:
no I/O, no shared mutable state, no locking. They are safe to call from any thread.

The mutable state around them is UI-thread-confined:

- `library_games`, `server_games_by_platform`, `installed_game_update_keys`, and
  `current_details_game` are all owned by the main window and mutated only from UI-thread
  handlers.
- The per-platform catalog fetch runs on a plain background thread but publishes through a
  signal; the handler that writes `server_games_by_platform` and calls
  `_refresh_installed_game_update_state` runs on the UI thread
  (grid-launcher.py:3124–3139).
- `_refresh_installed_game_update_state` mutates the installed records in place and
  rebinds `installed_game_update_keys` to a freshly built set (install_mixin.py:157),
  so a concurrent reader never observes a half-populated set — but it does observe
  half-updated `update_available` fields if it reads during the loop. Nothing does.
- `_details_update_available_for_game` mutates `installed_game_update_keys`
  incrementally (install_mixin.py:199–201) and is called from paint/refresh paths on the
  UI thread only.

The install/update pipeline is the one place where identity data crosses threads: the
finalize worker receives a **copy** of the game dict (install_mixin.py:1574) and returns a
new prepared record through its completion payload; registration into `library_games`
happens back on the UI thread. Full threading contract in
`docs/porting/08-background-threading.md`.

`_refresh_installed_game_update_state` is O(installed × server-entries) with an early exit
per match, and runs once per platform load completion, so a large catalog re-scans the
whole library once per platform.

## Open questions

1. **OPEN QUESTION: `lower` vs `casefold` in `game_key`.** `game_key` uses `str.lower`
   (identity.py:5) while every other normalization in the identity path uses `casefold`.
   Every test double uses `casefold`, so the difference is unpinned. A port must decide
   which is normative; the two disagree for non-ASCII titles.
2. **OPEN QUESTION: `game_key` has no type guard.** A non-string `title` or `platform`
   raises rather than degrading to `""`, unlike `rom_id_key` (identity.py:5 vs `:10–11`).
   Whether that is intentional strictness or an oversight is not stated.
3. **OPEN QUESTION: server lookup ordering.** `_server_game_for_identity`
   (grid-launcher.py:3399–3404) and `hydrate_install_game_metadata`
   (install_metadata.py:56) test ROM id and title/platform per entry rather than doing a
   ROM-id pass first. Combined with the non-deterministic insertion order of
   `server_games_by_platform`, the entry returned for an ambiguous game can vary between
   runs. It is unclear whether ROM-id priority was intended.
4. **OPEN QUESTION: two games sharing a title/platform pair.** Registration and
   normalization key on `game_key` only (install_mixin.py:126, config.py:186), so
   installing a second such game evicts the first record while leaving its files on disk.
   No test covers this and no user-facing message exists.
5. **OPEN QUESTION: positive-only update cache.** `_details_update_available_for_game`
   returns true straight from `installed_game_update_keys` without re-checking
   (install_mixin.py:185–186). If the server entry disappears or is rolled back between a
   full refresh and the details view opening, the button stays visible until the next full
   refresh; the action then reports "no longer available" (details_view_mixin.py:1818–1822).
   Whether the cache should be invalidated on catalog change is undecided.
6. **OPEN QUESTION: PC platform gap between detection and application.**
   `_is_windows_pc_platform` accepts `"pc"` (update_detection.py:80) but
   `is_native_executable_platform` requires the platform to start with `"windows"`
   (selection.py:150). A `PC`-labelled game can therefore be flagged via its filename tag
   but updated by full reinstall instead of the save-preserving merge.
7. **OPEN QUESTION: version-tag comparison ignores non-tag differences.** If both
   filenames carry the same tag but the server file differs otherwise, only the timestamp
   rule can catch it. No hash, size, or file-id comparison exists anywhere in the update
   path.
8. **OPEN QUESTION: naive timestamps assumed UTC.** `_parse_timestamp` attaches UTC to
   any timestamp lacking a zone (update_detection.py:92–93). Whether the RomM server ever
   emits local-time naive timestamps is not documented; if it does, comparisons are off by
   the offset.
9. **OPEN QUESTION: `revision` is displayed but never compared.** `game.json`'s `version`
   field lands in `revision` (install_metadata.py:155–156) and is shown as the version
   label fallback (grid-launcher.py:3294–3296), but no code compares an installed
   `revision` against a server one. For native games without a filename tag, only the
   timestamp rule applies.
10. **OPEN QUESTION: `revision` is not persisted.** `build_installed_game_record` writes
    it (install_registry.py:56) but `normalize_installed_games` drops it
    (config.py:152–184), so it is lost on the next load and must be re-hydrated from the
    server. Whether this is intentional is unclear.
11. **OPEN QUESTION: fallback version label crashes on semver.**
    `_default_details_version_label_text` formats the tag with an integer format spec
    (`f"Version: v{version_tag:05d}"`, game_views.py:264) although
    `rom_file_name_version` can return a string. Production always supplies
    `_details_version_label_text_for_game` (game_views.py:554–558), which handles both
    kinds, so the defective branch is unreachable today — but a port that omits the
    window-level override would hit it.
12. **OPEN QUESTION: PS4/Xbox 360 patch content and `update_available` are unrelated.**
    Installing `ps4_content`/`xbox360_content` never touches `update_available` or
    `server_updated_at`, and `ps4_has_update` means "patch files exist on the server", not
    "your install is out of date". The UI can therefore show both an "Update" button and
    an "Install Update" button with different meanings.
13. **OPEN QUESTION: TV frontend identity divergence.** The TV backend replaces installed
    entries by exact case-sensitive `id`/`rom_id` string equality
    (tv/bridge/game_backend.py:691–698) rather than `games_match_identity`. Records
    written by one frontend and read by the other can therefore be treated differently. No
    test covers cross-frontend consistency.
14. **OPEN QUESTION: no in-app self-update check.** The launcher never compares
    `__version__` to a remote value. Updating is entirely delegated to AppImage tooling
    reading the embedded `gh-releases-zsync` metadata (build.sh:228), and the `.zsync`
    delta file only exists for CI release builds (build.sh:229–238). Whether a port should
    add an explicit check is a product decision.
15. **OPEN QUESTION: `0.0.0-dev` is ambiguous.** It is both the source-checkout value
    (grid_launcher/__init__.py:15) and the git-unavailable build value (build.sh:94), so
    the string cannot distinguish "running from source" from "built without git".
