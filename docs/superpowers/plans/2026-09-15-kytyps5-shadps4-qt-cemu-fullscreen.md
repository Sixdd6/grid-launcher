> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax for tracking. One implementer at a time in the shared working tree. Commit each verified task with `git commit --only -- <paths>`. Never run `git checkout`, `git restore`, `git reset` or `git stash` on tracked files.

**Goal:** Cemu launches fullscreen and gets a real Windows asset pattern; KytyPS5 joins the catalog as the PlayStation 5 emulator with PS5 folder installs picking `eboot.bin`; the ShadPS4 Qt launcher installs on every OS, resolves its prerelease-only releases, is queued as a companion of a ShadPS4 catalog install, and is pointed at the installed shadPS4 build through `launcher/qt_ui.ini`.

## 1. Summary

Three catalog changes ship together. Cemu's profile args become `-f -g "%rom%"`, its dead `windows_assets` block becomes a live `asset_patterns` entry, and an existing config entry still carrying the old default `-g "%rom%"` is rewritten the next time the profile-defaults pass touches it. KytyPS5 is added as a GitHub-sourced catalog entry with per-OS assets, and PlayStation 5 base installs reuse the PS4 `eboot.bin` launch-file ranking without entering PS4 update/DLC content mode. The ShadPS4 Qt launcher loses its Windows-only gate, gains per-OS assets and prerelease resolution (including a forge fix, because GitHub's `/releases/latest` never returns a prerelease), is enqueued automatically after a ShadPS4 catalog install through a new `companions` profile key, and a new autoconfig writer keeps `<qt-dir>/launcher/qt_ui.ini` pointing at the installed shadPS4 executable in either install order.

## 2. Decisions taken while verifying the code

These are facts the task brief asked the planner to settle. Each is binding for the coder.

1. **Prerelease routing needs a forge change.** `crates/grid-core/src/launch/forge.rs::release_endpoint` maps a `latest` tag to `/releases/latest`. On GitHub that endpoint excludes prereleases, so `allow_prerelease: true` on the catalog entry is not enough: the request 404s before `source::select_release` (which already honours `allow_prerelease`) ever runs. `check_endpoint` / `ForgeClient::check_release_tag` (the "Update from Source" check) have the same gap. Fix: when the source allows prereleases and the tag is blank or `latest`, ask the `/releases` list instead, and let the check accept the list payload. The catalog entry keeps `release_tag: "latest"` so `catalog::configured_tag`, the install directory name (`<name>-latest`) and `source_release_tag` stay consistent with every other entry.
2. **Companion enqueue lives in grid-core, at admission time.** `InstallService::install_emulator` (`crates/grid-core/src/library/mod.rs`) admits the primary job, then admits each companion the profile names unless a config entry for it already exists. Reasons: (a) it is testable with the existing wiremock harness in `crates/grid-core/tests/emulator_install.rs`; (b) the queue is strictly serial — `pump` starts the next job only when both the download slot and the finalize slot are free — so the companion's finalize (and its `sync_new_emulator`) always runs after the primary's finalize has written the ShadPS4 entry; (c) `Admission::Duplicate` already dedupes a user who also clicks Install on the companion row; (d) the alternative, the `emulator_installed_hook` in `app/src-tauri/src/lib.rs`, is app-layer code with no test harness and it fires only after a successful primary finalize. Trade-off accepted: if the primary install fails, the companion still installs; the writer then finds no ShadPS4 entry and is skipped without a warning.
3. **`SyncContext` carries no emulator entries.** The brief said it does; it does not. `autoconfig::sync_new_emulator` loads `Config` itself and holds `config.emulators`. The counterpart lookup (ShadPS4 for a Qt launcher install, Qt launcher for a ShadPS4 install) reads that vector. No `SyncContext` change.
4. **The Cemu migration is data-driven.** A new optional profile key `legacy_args` (list of strings) is plumbed like `companions`. `autoconfig::entry::apply_manual_emulator_profile_defaults` replaces `args` when the trimmed current value is blank, exactly `%rom%`, or equals one of the profile's trimmed `legacy_args`. Cemu's entry lists `-g "%rom%"`. Any other custom args stay untouched. Reach: this pass runs from `sync_new_emulator` (catalog install, reinstall, "Update from Source") and from the manual save path in `app/src-tauri/src/commands.rs` (~line 1835). There is no startup repair pass, so an existing Cemu entry migrates on its next update or save — see Open Questions.
5. **Tar mode preservation needs no change.** `tar` 0.4.46's `Entry::unpack` always applies `mode & 0o777` (the `preserve_permissions` flag only governs setuid/setgid/sticky bits). The existing integration test `a_bare_executable_bit_member_is_selected_as_the_emulator` already pins this. A `.tar.gz` asset is stored as `<name>-latest.gz` (`emu_install::archive_file_name`, pinned by its test table) and `library/extract.rs::dispatch` sniffs the gzip magic, so extraction works regardless of the suffix.
6. **Qt INI line format.** Write `key=value` with no spaces, the same runtime form RPCS3's `CurrentSettings.ini` uses (`emulator-autoconfig` skill). `writers::rpcs3_gui_section(raw, section, desired, false)` produces exactly that; add a thin, documented alias `writers::qt_plain_section` so `shadps4_qt.rs` does not call an RPCS3-named function.
7. **PS5 gets its own finalize branch.** It shares the extract-and-pick logic with `finalize_ps4_base` but records no `ps4_game_id` and `content_mode` stays PS4/Xbox-360 only, so a PS5 row never offers update/DLC content.
8. **shadPS4 user dir.** Create `<shadps4-dir>/user/` next to the installed shadPS4 executable so the emulator is portable and the profile's `save_directories: ["user/home/1000/savedata"]` resolve to that folder. The Qt launcher has no known setting for the user dir; it uses `<cwd>/user` when present, else the XDG/APPDATA dir. GRID launches the Qt launcher with cwd = its own directory, which is a different directory from shadPS4's, so the launcher's own game list may come from the XDG/APPDATA dir while games launched by GRID use the portable one. Documented as a known limitation (Risks, Open Questions), not solved here.

## 6. Risks & Edge Cases

- **Alphabetical tie-break fragility (being replaced).** Today `select_executable` ranks `kyty_emulator` above `launcher` only because `k < l`; `select_asset` picks Cemu's Windows asset by name order because there is no pattern. Preferred names (3.2) and `asset_patterns` (2.1) remove both accidents. Other entries still using `windows_assets` (Azahar, Eden, Vita3K-style blocks) keep the old behaviour; out of scope, noted for a follow-up.
- **Prerelease-only repos.** Without 4.5/4.6 the Qt launcher install and its update check 404 on `/releases/latest`. With the list endpoint, GitHub returns newest-first; `select_release` takes the first non-draft. A repo that mixes drafts and prereleases is covered by the test in 4.7. The list endpoint returns 30 releases by default — enough; do not add paging.
- **Qt INI escaping.** QSettings escapes `\` in values and may lowercase or re-order keys when it rewrites the file. Writing forward slashes avoids the escaping; the writer must tolerate a file Qt has rewritten (the key regex `[A-Za-z0-9_]+` matches `versionSelected`; if Qt adds a `%General`-style section or `\default` lines, the plain writer strips only the managed keys' annotations). Overwrite policy: this INI family REPLACES managed keys — that is intended here (GRID owns `versionSelected`); every other key is preserved (test 6.3).
- **`versionPath` semantics.** Verified only as "the folder holding versions, optional". If the launcher lists that folder's subdirectories as versions, pointing it at the shadPS4 executable's parent shows an odd list but does not break `versionSelected`. Flagged as an open question.
- **Portable-mode dependence on cwd.** The launcher reads `<cwd>/launcher/qt_ui.ini` only when started with cwd = its directory. GRID's standalone launch sets that cwd (`launch/spawn.rs::prepare_standalone_emulator_launch`); a user double-clicking the AppImage from a file manager gets a different cwd and the XDG/APPDATA settings instead. Documented in the module doc.
- **Two user dirs.** shadPS4 gets `<shadps4-dir>/user/`; the launcher has no known user-dir setting and lives in another directory, so its own library view may read the XDG/APPDATA dir. Games GRID launches go through the shadPS4 entry and use the portable dir, which is what the profile's `save_directories` point at. Known limitation.
- **Tar mode preservation.** Verified in `tar` 0.4.46 source: `_set_perms` applies `mode & 0o777` unconditionally on unix. Pinned by the existing `a_bare_executable_bit_member_is_selected_as_the_emulator` and the new 3.7 test. No extraction change.
- **`.gz` archive name.** `archive_file_name` yields `KytyPS5 (Playstation 5)-latest.gz`; `should_extract("Emulator", ...)` accepts `gz`; `dispatch` sniffs gzip. Parentheses in the install dir name are already exercised by the Redream row in the naming table.
- **Companion when the primary fails.** The companion still installs (Decision 2). The launcher's sync then finds no ShadPS4 entry and writes nothing, with no warning. A later ShadPS4 install completes the pairing (6.5, second order).
- **Companion on update.** `update_emulator` re-installs through `install_emulator`, so a user updating ShadPS4 without the launcher gets the launcher queued. Acceptable; documented in 5.2.
- **Migration reach.** No startup repair pass exists; a Cemu entry migrates on its next update, reinstall or manual save. See Open Questions.
- **PS5 title ids.** `specials::ps4::detect_title_id` would match `PPSA12345`; the PS5 branch deliberately does not call it, so `ps4_game_id` stays blank and no content UI can attach to a PS5 row.
- **Profile order.** The ShadPS4 entry must stay before the Qt launcher entry and KytyPS5 must not collide with either (`kyty_emulator` shares no token). The integrity test in 1.3 and the `profile_for_entry` tests in 3.9/6.4 guard this.
- **IPC shape.** Both new profile fields are `skip_serializing`; `ProfileSummary` and the catalog `CatalogEntry` shapes do not change. `check_release_tag` is not a command; only its Rust caller changes.
- **Secrets.** Nothing here touches credentials. The forge sends no `Authorization` header (existing test); the new writer writes paths only. `scripts/check_secret_hygiene.sh` is unaffected.
- **Layering.** All new logic is in `crates/grid-core`; `app/src-tauri` changes are a one-argument pass-through. grid-core gains no Tauri dependency.
- **E2E fixtures.** No spec enumerates the catalog; `content-seed.mjs`'s comment about `WINDOWS_ONLY_SLUGS` (Xenia Canary) stays true.

## 7. Open Questions

1. Should a one-time startup repair pass migrate existing Cemu entries (`-g "%rom%"` → `-f -g "%rom%"`) before the user next updates or saves the entry? Not in this plan; add as a follow-up if wanted.
2. Does the Qt launcher expose a user-directory setting in `qt_ui.ini`? If it does, `ensure_version_selected` should also write it to `<shadps4-dir>/user` so both tools share one library. Needs a live check of the launcher source; until then the limitation in Decision 8 stands.
3. `versionPath` semantics (see Risks). If it must be a directory of version subfolders, drop the key and write `versionSelected` alone.
4. Should the Qt launcher entry's `save_directories` be cleared (it inherits ShadPS4's `user/home/1000/savedata`, which resolves against the launcher's own directory and will never hold saves)? Harmless today; a cleanup candidate.
