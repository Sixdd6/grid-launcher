# Library layout v1 — Implementation Plan (2026-09-15)

> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax for tracking. One implementer at a time in the shared working tree. Commit each verified task with `git commit --only -- <paths>`. Never run `git checkout`, `git restore`, `git reset` or `git stash` on tracked files.

**Goal:** Deleting an emulator never deletes its saves, settings or firmware. The library root becomes `games/`, `emulators/` and `saves/`; every directory an emulator writes beside its binary lives under `saves/<Emulator>/` and is reached through a link from the install directory; an existing library migrates itself once, at startup, and resumes after an interruption.

**Architecture:** All layout rules, the link primitive and the migration live in `crates/grid-core` (`library::paths`, a new `library::user_data_links`, a new `library::layout_migration`); the catalog gains one data key (`user_data`). `app/src-tauri` only decides *when*: it runs the migration in `lib.rs::run()` before the services are built and exposes the failure message through one pull command, which the frontend turns into one long-lived toast. Games keep their internal shape; only the prefix moves, so the resolution fallbacks try `games/<Platform>` first and the legacy `<Platform>` second.

**Spec:** `docs/superpowers/specs/2026-09-15-library-layout-v1-design.md` — binding. This plan records the mechanics, verified against the code on 2026-09-15.

**Gate (from the repo root, per `CLAUDE.md`):** `scripts/check_secret_hygiene.sh`, `cargo fmt --check`, `cd app && npm ci && npx svelte-check && npm run build`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo clippy -p app --all-targets --features e2e -- -D warnings`, `cargo test --workspace`, `cd app && npm test`. Then the full e2e run (`scripts/e2e.sh`, full build — Rust and seeds change). End with `cargo clean --profile dev`.

## Global constraints (from the spec)

- `crates/grid-core` stays Tauri-free. The migration, the links and every path rule are grid-core; `app/src-tauri` is wiring only.
- Windows uses NTFS directory junctions through the `junction` crate (needs no privilege). Never a Windows symlink. The crate is a `[target.'cfg(windows)'.dependencies]` entry in `crates/grid-core/Cargo.toml`.
- Every migration step is idempotent and every move is a same-filesystem `std::fs::rename` inside the library directory. A `CrossesDevices` rename aborts.
- Secrets never reach a log line, an error message or an IPC payload. Migration logs carry paths only.
- Commit with `git commit --only -- <paths>`; one implementer at a time in the shared tree.

## 1. Summary

The library root is reorganized into `games/<Platform>/`, `emulators/<Emulator>/` and `saves/<Emulator>/<dir>/`, where `<Emulator>` is the sanitized catalog PROFILE name with no release tag. Each catalog profile lists the directories the emulator writes beside its binary (`user_data`); on install, update and migration those directories are moved under `saves/` and replaced by links, so `delete_emulator` removes links as links and the data survives, and a reinstall finds it again without a download. A salvage pass before removal catches anything the list misses. Existing libraries migrate once at startup, driven by `Config::library_layout_version` (0 → legacy, 1 → this layout), with every step resumable and a failure surfaced as one startup toast while the legacy fallbacks keep the library readable.

## 2. Decisions taken while verifying the code

Each item is binding for the coder. Line numbers are as of 2026-09-15.

1. **Cloud sync already walks through links; no walker fix is needed.** `cloud/dirs.rs::expand_sync_path` (:377-416) ends in `generic_candidate` (:340-348), which calls `autoconfig/paths.rs::resolve_best_effort` (:261-272). That function walks `join_realpath` (:192-245), which `lstat`s every component and, for a symlink, recurses onto `read_link`'s target — absolute targets reset the path, relative targets are walked from the link's own parent (doc comment :150-191). So `<library>/emulators/PCSX2 (Playstation 2)/memcards` resolves to `<library>/saves/PCSX2 (Playstation 2)/memcards` BEFORE `cloud/mod.rs::latest_mtime_under` (:151-193) sees it, and that walker's "never descend into a symlinked dir" rule (:173-179) is irrelevant because the root it is handed is already the real directory. Nested profile paths (`memstick/PSP/SAVEDATA` under a linked `memstick`) resolve the same way: the link is the first component. Same for `resolved_screenshot_directories` (:609). `ResolveContext::emulator_dir` comes from `cloud/ops/mod.rs::emulator_dir_for` (:220-225), a plain `parent()`, so it is the install dir, not a canonical path. Pinned by the new cloud test in Task 4 (4.7).
2. **Windows junctions are handled by both `resolve_best_effort` and `remove_dir_all`.** Rust's std treats a junction (mount-point reparse point) as a symlink for `symlink_metadata().file_type().is_symlink()` and `read_link` (name-surrogate reparse tags), so `join_realpath` follows it. `std::fs::remove_dir_all` documents "does not follow symbolic links and it will simply remove the symbolic link itself"; the Windows implementation (`library/std/src/sys/fs/windows/remove_dir_all.rs`) opens every entry with `FILE_OPEN_REPARSE_POINT` and `OBJ_DONT_REPARSE` and deletes the reparse point itself (the CVE-2022-21658 fix, Rust 1.58.1). `library/mod.rs::remove_dir_tree` (:3037-3046) is a thin wrapper over it, and `emulator_removal.rs::apply_removal` (via `library/mod.rs:2710`) uses it, so removing an install directory removes the links, never the `saves/` targets. Still, `user_data_links.rs` uses `junction::exists`/`junction::get_target` for its own checks on Windows rather than relying on std's reparse-tag classification (Task 4).
3. **Config today.** `Config` (`config.rs:151-260`) has no layout field; `library_path` is a raw string, `~/` is expanded only at read sites (`library/paths.rs::expand_home` :90-97, `pub(crate)`; `library_root` :106-111 is the public wrapper; `InstallService::library_root` `library/mod.rs:1360-1366`). `Config::default_path` (:319-327) honours `GRID_LAUNCHER_DATA_DIR`. The `set_library_path` command (`app/src-tauri/src/commands.rs:499-509`) assigns the string through `config_write::modify_config` and nothing else. `[ui]` is a TOML table, so the new scalar `library_layout_version` MUST be declared before `ui` in the struct (comment at `config.rs:253-256`). Registry rows store the EXPANDED library root (`library_root()` output joined by `path_string`), while `config.library_path` may still say `~/...`; the rewrite in Task 7 matches both spellings.
4. **The `set_library_path` rule is filesystem-based, but only there.** The spec forbids directory sniffing at STARTUP (numeric compare only) and requires `set_library_path` to distinguish a fresh directory from a legacy library, which needs one `read_dir`. Rule (`paths::layout_version_for_library_path`): version 1 when the path is blank, does not exist, is not a directory, has no entries other than dot-entries, or already contains any of `games`, `emulators`, `saves` at the top level; otherwise 0. Consequence: pointing the config at a populated directory that is NOT a GRID library gives version 0, but the reference-driven migration (Decision 15) finds nothing to move there and stamps version 1 after a no-op run.
5. **Startup notice pattern: the python-import pull, not the self-update badge.** `lib.rs:97-106` computes `python_import` before the services and stores it in `AppState.python_import: Option<ImportReport>` (`commands.rs:79`); `commands/updates.rs::python_import_notice` (:95-98) returns it; `app/src/lib/stores/pythonImport.svelte.ts` pulls it once from `App.svelte:46-48` and pushes one toast (`pushToast(text, level, 20000)`). The self-update badge (`Shell.svelte:155-167`, `appUpdate.svelte.ts`) is an event-plus-pull design for a check that runs AFTER the webview exists; the migration finishes before the window is created, so the pull-only pattern is the right one. `Toast.svelte` has no click-to-dismiss (only `data-testid="toast"` paragraphs); "dismissible" is met by the auto-dismiss, same as the import toast. No new component; no designer step.
6. **`Registry` has no transaction API and its `conn` is private.** `registry.rs:389-391` holds `Mutex<Connection>`; migrations use `conn.transaction()` internally (:135, :158, ...). Rows have an `id INTEGER PRIMARY KEY`. Task 7 adds `Registry::rewrite_paths(&self, rewrite: &dyn Fn(&str) -> Option<String>) -> Result<usize, LibraryError>` that runs one transaction over the nine path columns (`ps3_trophy_paths` is a JSON array of strings — `library/mod.rs::parse_trophy_paths` :2801-2808 — rewritten element-wise). The closure keeps the registry ignorant of layout names. No schema change, no `user_version` bump.
7. **Dropping the tag is one call-site change.** `emu_install::emulator_install_dir(library, archive_stem)` (`launch/emu_install.rs:33-37`) has two production callers: `library/mod.rs:2518-2527` derives `stem` from `archive_file_name(profile_name, configured_tag, "")` and passes it; `emu_install::install_manual_archive` (:66) passes the ENTRY name (unchanged behaviour). Task 2 renames the parameter to `name`, joins `emulators/`, and `resolve_emulator_download` passes `&job.profile_name` directly; the `dir_name`/`stem` pair at :2518-2519 goes away (the archive FILE name at :2529-2531 still carries the tag, by design). `compat_tool_install_dir` (:43-45) and the compat root are untouched — the spec does not cover compat tools.
8. **`profile_for_entry(entry_name: &str, exe_path: &str, profiles: &'a [EmulatorProfile]) -> Option<&'a EmulatorProfile>`** (`launch/profiles.rs:386-430`): name match first, then executable basename against tokens (glob-aware), then stem. Two config entries with different names but the same executable resolve to the same profile, which is what makes "two entries, one directory" collapse to one `<Emulator>`.
9. **Dolphin is NOT in the catalog.** `emulator-autoprofiles.json` has no profile whose name or tokens mention Dolphin (case-insensitive search: zero hits); `autoconfig::is_dolphin` (`autoconfig/mod.rs:284`) matches by token/name only and `autoconfig/dolphin.rs` writes settings for hand-configured entries. There is no catalog row to attach `user_data: ["User"]` to, and no GRID code path creates one directory shared by two Dolphin entries: a manual-archive install lands in `emulators/<ENTRY name>` (Decision 7). The spec's Dolphin row and its two-entries-one-directory example therefore have no implementable target today. Ruling (orchestrator, 2026-09-15): no catalog row. The Dolphin row is dropped from Task 3, the migration still handles "two config entries under one directory" generically (Task 7, 7.3), and a hand-configured Dolphin is protected by the hand-configured rule (never moved, linked or deleted). `emulator_removal.rs` test (f) (:253-264) keeps modelling the shared-directory case.
10. **Xenia Edge is in the catalog** (`emulator-autoprofiles.json:488-513`, same `content`/`screenshots` shape as Xenia Canary) but not in the spec's table. Task 3 gives it the Xenia Canary row (`content`, `cache`). Confirmed by the orchestrator.
11. **`merge_tree_into` is dest-loses.** `library/mod.rs:2946-2971`: a destination file or directory with the same name is deleted before the source is renamed over it. That is right for archive staging but wrong for user data — a reinstalled archive that ships a default `inis/` or `config/` would overwrite the user's saved settings. `ensure_user_data_links` therefore uses its own `move_tree_preferring_dest` (Task 4): a conflicting SOURCE file is dropped, the existing destination file stays. `merge_tree_into` stays private and unchanged.
12. **Unix links are RELATIVE (`../../saves/<Emulator>/<dir>`); junctions are absolute.** A relative symlink survives moving or renaming the whole library directory. `join_realpath` walks a relative target from the link's parent (Decision 1), so the cloud path still resolves. "Already points at the right target" is decided by comparing `canonicalize(link)` with `canonicalize(saves_sub)`, not by comparing link text. Windows junctions store an absolute target by design.
13. **`Emulators` → `emulators` needs no two-step on Linux, and the fallback must not use `Path::exists`.** On a case-sensitive filesystem `rename("Emulators", "emulators")` succeeds directly. On a case-insensitive one the same call may succeed (APFS and NTFS both allow case-only renames) or fail with `AlreadyExists`/`PermissionDenied`; only on such a failure does the migration go through the fixed temporary name `.grid-layout-emulators-tmp` (fixed, so a resumed run can find and finish it). Existence checks in the preflight and the steps compare EXACT names from `read_dir`, because `Path::exists("emulators")` is true on a case-insensitive filesystem whenever `Emulators` exists.
14. **A missing library directory is "nothing to do", not a failure.** The e2e `python-import` stage imports a config whose `library_path` (`scripts/e2e.sh:567`) does not exist on disk, and a user whose library lives on an unmounted drive would otherwise see the failure toast on every start. `layout_migration::run` returns `Skipped` (debug log, no notice) when the directory is absent, leaves the version at 0 and retries next start. Only a collision or an I/O error yields `Failed` and the toast.
15. **The migration is reference-driven: both the game set and the emulator pairs are derived from data, never from a directory listing or from what this run did.** The GAME set is the set of top-level names `X` such that some registry path column (the nine in Decision 6), or some config value in `native_manual_save_paths`, `native_pcgw_save_paths`, `native_removed_save_paths`, `emulators[].save_paths` or `emulators[].state_paths`, has `<library>/X/` as a prefix — plus the fixed name `PlayStation 3` when `<library>/PlayStation 3/.vfs` exists (the RPCS3 vfs target). Names in {`games`, `emulators`, `Emulators`, `saves`} and dot-prefixed names are excluded. An unreferenced top-level directory is left where it is. The EMULATOR pairs `(legacy dir name D → new name N)` come from the config entries plus what is on disk (`emulators/N` exists and `emulators/D` does not). Both derivations are deterministic across runs, so every step is idempotent; a resumed run finds a moved `X` as "`games/X` exists, `X` does not — done". When both derivations are empty the run still stamps version 1 (a no-op run on a fresh or foreign directory is a completed run).
16. **Config fields rewritten go beyond the spec's three.** `native_manual_save_paths` and `native_pcgw_save_paths` (`config.rs:203-238`) hold absolute save paths that, for a native game, usually sit inside `<library>/<Platform>/<Title>/...`; leaving them stale would break native cloud sync after the move. Task 7 rewrites them with the same rule. `cloud_sync_state` holds no paths and is left alone.
17. **Salvage when a directory resolves to the install dir itself.** Redream declares `state_directories: ["."]` (`emulator-autoprofiles.json:579-581`) and xemu declares `screenshot_directories: ["."]` and `firmware_directories: ["."]` (:362-363); their user data (`vmu0.bin`, `redream.cfg`, `flash.bin`, `xbox_hdd.qcow2`, `eeprom.bin`, `xemu.toml`) are loose FILES beside the binary. Rule: a resolved directory strictly inside the install dir is moved whole to `saves/<Emulator>/<rel>`; a resolved directory EQUAL to the install dir salvages only its top-level regular files, excluding the entry's executable and anything `library::extract::is_extractable_archive` recognizes (and `.AppImage`), into `saves/<Emulator>/`. This satisfies the spec's Redream test and never moves the install directory into itself.
18. **The e2e seeds switch to the new shape; one new stage seeds a legacy library.** Five seeds write `<library>/<Platform>/...` and registry rows pointing there (`launch-seed.mjs:50,75,157`, `emulator-catalog-seed.mjs:44,49,109`, `images-seed.mjs:43,46,108`, `cloud-saves-seed.mjs:108,110,186`, `updates-seed.mjs:67,78-81,147,154-155`) with no `library_layout_version`, so the migration would run at their startup and move everything before their specs assert. To keep those stages testing what they test, they write `games/<Platform>/...` plus `library_layout_version = 1`; the migration itself is covered by the new `layout-migration` stage (Task 8). `e2e/seed/registry-schema.mjs` says the `launch`, `cloud-saves` and `images` seeds keep v1 databases on purpose; the layout change is data-only, so that stays true.
19. **`BUILD.md` has no e2e group list to extend** (:92-94 points at `STAGE_GROUPS` in `scripts/e2e.sh`). Task 9 touches `BUILD.md` only if a sentence about seeds needs the new stage; otherwise no change. `ARCHITECTURE.md` has no layout section; Task 9 adds one under "User state".
20. **`ErrorKind::CrossesDevices`** is stable since Rust 1.85. If the workspace toolchain is older, match `raw_os_error()` `18` (`EXDEV`) on unix and `17` (`ERROR_NOT_SAME_DEVICE`) on Windows instead. Check `rustc --version` before choosing.
21. **`junction` crate: version 2.0.0** (crates.io, released 2026-05-01; repo `tesuji/junction`). API: `junction::create<P: AsRef<Path>, Q: AsRef<Path>>(target: P, junction: Q) -> io::Result<()>` (errors if `junction` exists), `junction::delete<P>(junction: P) -> io::Result<()>`, `junction::exists<P>(junction: P) -> io::Result<bool>`, `junction::get_target<P>(junction: P) -> io::Result<PathBuf>` (works even when the target is gone). The crate root is `#![cfg(windows)]`; placing it under `[target.'cfg(windows)'.dependencies]` keeps it out of the Linux build entirely, so `cargo clippy` on Linux never type-checks the Windows arms — see Risks.

## 6. Risks & Edge Cases

- **Interrupted migration mid-rename.** A single `rename` is atomic on every supported filesystem; a crash between steps leaves a mix of moved and unmoved directories, the version at 0, and the config/registry unrewritten. Every step is idempotent and derives its work from disk + config (Decision 15), so the next start finishes it. The one non-atomic moment is the two-step root rename; the fixed temp name makes it resumable. Pinned by `an_interrupted_run_resumes_to_the_same_end_state` and `the_temp_name_fallback_finishes_a_half_done_root_rename`.
- **Case-insensitive filesystems.** `Path::exists("emulators")` lies when `Emulators` exists; every collision and existence check uses exact `read_dir` names (Decision 13). The two-step rename is taken only when the direct rename fails. Windows CI has never compiled this workspace (memory), so the Windows arms are unproven until it does.
- **Hand-made symlinks inside the library.** Step 1 renames only the derived names (Decision 15) and only when `DirEntry::file_type()` `is_dir()` — a symlinked directory at a derived name is a symlink, not a dir, and is left in place with a warning; unreferenced entries and files are never touched. Inside an install directory, a user's own symlink at a `user_data` name is treated as "a link to the wrong target" and REPLACED by `ensure_user_data_links` (spec rule 4); its old target is not touched. `move_tree_preferring_dest` moves symlinks as themselves and never follows them.
- **`remove_dir_all` on a junction / symlink.** Removes the link, never the target (Decision 2, std docs and the Windows implementation). `remove_dir_tree`'s `PermissionDenied` retry calls `make_tree_writable`, which skips symlinks (`library/mod.rs:3048-3051`), so it cannot chmod inside `saves/`.
- **Cloud sync through links.** Works by construction (Decision 1); pinned by 4.3. A profile path that names the install dir itself (`.`) resolves to the install dir, so xemu/Redream sync behaviour is unchanged; their loose files are protected by salvage (Decision 17), not by links.
- **Emulator configs with stale absolute paths beyond the three rewritten.** RPCS3 `portable/config/games.yml` (written by `autoconfig/rpcs3.rs::update_games_yml`, absolute `<lib>/PlayStation 3/.vfs/dev_hdd0/game/<id>` paths) IS rewritten with the same text rule (Task 7). RetroArch `retroarch.cfg` directory keys and DuckStation `settings.ini` paths point INSIDE the install dir (now through links) and keep working. Cemu `settings.xml` `mlc_path` if absolute is stale — same class. Out of scope per spec.
- **Dolphin shared directory.** No catalog row (Decision 9); the generic two-entries case is handled and tested; Dolphin gets no links until a profile exists.
- **Foreign directory pointed at by `set_library_path`.** A populated non-GRID directory gets version 0 (Decision 4); at the next start the reference-driven migration derives an empty game set and no emulator pairs, moves nothing, and stamps version 1 (Decision 15). Pinned by `a_library_with_no_references_becomes_version_1_without_moving_anything`.
- **E2E fixture churn.** Eight seeds and nine specs change; a missed one shows up as a moved-path assertion failure, not a silent pass. The new stage is the only one that exercises the migration; the others assert the v1 shape directly.
- **Windows CI unproven.** The `junction` dependency and the `#[cfg(windows)]` arms compile only there. Mitigation: keep every Windows arm tiny and behind the four primitives in `user_data_links.rs`; if a Windows toolchain is available locally, `cargo check -p grid-core --target x86_64-pc-windows-msvc`.
- **`sanitize_component` collisions.** Two profiles whose names sanitize to the same string would share `emulators/<N>` and `saves/<N>`. The catalog has none today; Task 3's `profile_names_sanitize_uniquely` asserts it.
- **Signature change fan-out.** `remove_emulator_files` gains two parameters (one production caller in `commands.rs`, one test caller); `emulator_install_dir`'s parameter is renamed (two callers). Both are compile-time checked.
- **Secrets.** Nothing here touches credentials. The migration logs and the notice carry paths only; `scripts/check_secret_hygiene.sh` is unaffected. `rewrite_paths_in_text` runs on three emulator config files that hold no tokens (PPSSPP's `ppsspp_retroachievements.dat` is not one of them).
- **Layering.** All new logic is in `crates/grid-core`; `app/src-tauri` adds one call, one `AppState` field and one command. grid-core gains no Tauri dependency; the `junction` dependency is Windows-only.
- **Config write concurrency.** The migration writes `config.toml` from `run()` before the Tauri builder exists, so `config_write::lock()` is not needed there; every later write goes through `modify_config` as today.
